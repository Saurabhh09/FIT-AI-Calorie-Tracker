# FITAI production blockers

**Snapshot date:** 2026-10-04. This is a risk/status list, not a production-readiness declaration.

| Area | Current state | Required before production |
|---|---|---|
| Supabase project and secrets | No project credentials are configured. Only public URL/anon-key placeholders exist in `.env.example`. | Create a non-production project first; configure server/browser-safe variables; verify project settings, email allowlist, backups, and access controls. Never expose service-role credentials. |
| SQL migrations / RLS | `supabase/migrations/202610030001_initial_schema.sql` is a draft and has not been run against Postgres. | Apply only to a disposable development project, review generated schema/trigger behavior, test same-user and cross-user access for every table, and rehearse rollback/restore. Seek explicit approval before any production migration. |
| Authentication | Signup/login/logout routes, strict request schemas, native form fallback, and a Next 16 Proxy session-refresh path are implemented and locally tested. No real Supabase session has been exercised. | Test email confirmation, expired/rotated sessions, reset flow, enumeration behavior, cookie settings, account deletion/export, and durable rate limiting. Configure redirect URLs and email delivery. |
| Onboarding | Goal-first UI and an RPC call exist; saving requires the unapplied migration. | Test all paths with real sessions, age-band updates, retry/error behavior, accessibility, and migration rollback. Decide whether under-13 users can create accounts and how age is verified. |
| App data persistence | Dashboard is intentionally a placeholder. Meal logging, hydration, weight entries, recipes, preference updates, and their routes/UI are not migrated. | Implement validated owner-scoped APIs, persistence, history/versioning, export/delete paths, and RLS integration tests. |
| USDA data | Authenticated server-side search is implemented, but no Data.gov key is configured and search results contain source identity only. No detail import, nutrient-basis normalization, caching, or production records exist. | Configure server-only key; implement detail fetch and documented per-100 g/serving normalization; store checksum, source/version, basis, and verification metadata; add durable rate limiting/cache; evaluate non-US/Indian food coverage. |
| Nutrition references | Calculator supports sourced per-100 g nutrient facts; no reference targets or target formulas are loaded. | Select current jurisdiction-appropriate references, store source/version/age/sex/life-stage ranges, validate units and calculations with a qualified reviewer, and never fall back to adult targets for minors. |
| AI interpretation | No model is called. Environment variables are placeholders. | Select and approve provider/privacy terms; build server-only adapter, structured schema, timeout, retry, usage/cost limits, redaction/retention policy, uncertain-ingredient confirmation, and tests proving AI cannot create or change nutrition totals or bypass restrictions. |
| Allergies / restrictions | Schema can store self-reported allergy labels; there is no verified allergen mapping or safety filter yet. | Implement conservative ingredient matching and uncertainty escalation, clearly state limits, test every search/logging/recommendation path, and do not claim allergy-free safety. |
| Minors / medical claims | Age-band safeguards block restrictive weight-loss goals for under-18/unconfirmed bands in UI/domain rules and draft SQL. No personalized target engine exists. | Legal/clinical review of age controls, age-appropriate references, supported claims, parental/guardian policy, and handling of users who withhold age. |
| Privacy/security/operations | Bounded input schemas, origin checks, server-side secrets, Proxy cookie refresh, private/no-store API responses, and baseline security headers exist. Durable throttling, CSP, observability, restore drills, and formal privacy controls are not complete. | Threat-model the app; add rate limits/WAF, CSP, monitoring/alerting, backup and restore evidence, data retention/consent, incident response, and a privacy review. |
| Hosting/deployment | No hosting project is configured; local build only. | Add CI and staging, environment separation, database backup policy, accessibility/security scans, documented deploy/rollback, and explicit user approval. |

The successful local build, passing domain tests, and zero npm audit findings are useful checks, but they do **not** resolve the blockers above or establish production readiness.
